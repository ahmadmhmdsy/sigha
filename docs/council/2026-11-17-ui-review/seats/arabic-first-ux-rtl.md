# Seat: Arabic-first UX & RTL Correctness

Read-only review of `app/src/main/java/com/sigha/converter/ui` (20 files), `res/values*/strings*.xml`, `ui/theme`, and the shipped asset/QA surfaces they render. Every claim below was read in the file named; anything that needs a rendered screen says so.

## Verdict

This is a real Arabic UI, not a translated one: 218/218 keys present with identical format specifiers, zero hard-coded Compose text, correct `start`/`end` structure and auto-mirrored navigation — better than most Arabic Android apps in the region. But the localisation stops exactly where the app starts doing work: the note attached to a finished conversion, the OCR pack's name, the privacy-policy body and the raw engine details are all produced in English, and every count in the UI is ungrammatical because the project contains not one Arabic plural form. So the Arabic-first user's defining act — scan a page, read Arabic text — can return Latin gibberish explained in English, and the app's own verification document contains no Arabic or RTL evidence at all.

## Strengths

1. **Parity is total and mechanical, not aspirational.** Programmatic diff of key sets and format specifiers: `strings.xml` 165/165, `strings_ui.xml` 31/31, `strings_legal.xml` 22/22 — 0 missing, 0 extra, 0 specifier mismatches (`app/src/main/res/values-ar/strings.xml` vs `values/strings.xml`). A grep for literal `Text("` / `contentDescription = "` strings across `ui/` returns one hit, a bullet glyph (`ui/PrivacyScreen.kt:187`).
2. **RTL is structural.** `android:supportsRtl="true"` (`app/src/main/AndroidManifest.xml:17`); every inset uses `start`/`end` or `horizontal` — grep for `.left(` / `.right(` / `absoluteOffset` in the whole app returns 0 hits; the back arrow and all four chevrons use `Icons.AutoMirrored` (`ui/components/Common.kt:73`, `ui/QueueScreen.kt:220`, `ui/HistoryScreen.kt:207`, `ui/SettingsScreen.kt:407`). Nothing here needs retrofitting.
3. **The prose is native MSA, and the failure taxonomy is localised correctly.** `app_tagline` "حوّل على هاتفك. لا تُرفَع ملفاتك." (`values-ar/strings.xml:6`), `workbench_no_target` (`:49`), correct passive "أُلغي التحويل" (`:70`), correct gender agreement on the theme chips "فاتحة"/"داكنة" (`:106-107`), Arabic comma (`:57`). Failures map from typed kinds to resource IDs at the UI layer (`ui/FailureUi.kt:12-28`) — the right pattern, and the one the notes below fail to follow.

## Persona red flags

**Umm Ali, 34, Baghdad — phone-shop paperwork, Arabic-only, Samsung A14.** She opens Settings → "حزم النماذج" and the only pack is titled "OCR: English + Arabic" with an English description, so she taps "تنزيل" on faith. She then converts a scanned Arabic ID: Tesseract runs with the default `eng` model (finding 5), the "result" is a TXT of Latin noise, and the only explanation is "ملاحظة: No text layer found; used OCR." (finding 1). Her conclusion is not "a setting is wrong" — it is "this app does not do Arabic", the one promise the product is built on.

**Haidar, 27, Basra — bilingual, phone set to English.** He never sees the Arabic UI and there is no way to switch it (finding 10), so the Arabic build ships unreviewed by its own audience. If he later switches the phone for family use, Settings → "سياسة الخصوصية" opens Arabic chrome over an English policy (finding 4) — the exact "machine-translated menu" experience `PRODUCT.md:22` says Sigha exists to beat.

## Qiyas cards

### Card 1 — Localise the note at the layer that knows the locale (fixes finding 1)

- **Al-Far' (proposal):** replace the free-text `note: String?` on `ConversionResult`/`QueueEntry` with `NoteKind` + typed args, resolved to a string only in the composable, and delete the English literals in the four producers.
- **Al-Asl (real precedent):** the app's own failure path already does exactly this — `ConversionFailureKind` → `headlineRes()` (`ui/FailureUi.kt:12-28`), where the engine populates an enum and the UI translates. The broader platform precedent is Android's own split: `MediaPlayer`/`MediaStore` report `MEDIA_ERROR_*` integer codes and never a user-facing sentence, precisely because a system library has no locale.
- **Al-'Illa (causal invariant):** user-visible text must be chosen where the locale is known; text produced where no `Context`/`Configuration` exists can only ever be in the developer's language. The defect is architectural, not lexical — which is why three screens repeat it.
- **Conditions (شروط):** every note producer enumerated first (`model/OcrPageRange.kt`, `engine/media/VideoConverter.kt`, `engine/pdf/PdfToTextConverter.kt`, `engine/archive/ArchiveConverters.kt`); each note kind gets a `values-ar` string; a test asserts the UI never receives raw producer text; `docs/qa/verification.md:165-166` is corrected in the same change, since it currently promises behaviour the code does not have.

### Card 2 — Make Arabic plurality a type, not a string (fixes finding 3)

- **Al-Far' (proposal):** every counted string becomes a `<plurals>` with the six Arabic categories, consumed through `pluralStringResource(R.plurals.x, count, count)`; no counted sentence may remain a `<string>`.
- **Al-Asl (real precedent):** Android's platform `plurals` resource contract, which encodes CLDR's six Arabic categories by design and is what AOSP Settings and Gmail's Arabic UI use; on the Compose side `pluralStringResource` is the standard accessor. The app already trusts this mechanism nowhere and the platform everywhere else (it uses `stringResource` for 218 strings).
- **Al-'Illa (causal invariant):** Arabic agreement is a function of the count modulo 100, not of `n == 1`; a single-form string has one degree of freedom where the grammar has six. Adding an `if (n == 1)` branch — the shortcut `ui/WorkbenchScreen.kt:674` already takes for the Convert button — fixes only the duals of the symptom and still breaks at 2, 11, 100.
- **Conditions (شروط):** define zero and two explicitly (Arabic renders 2 as a dual noun, not "2 ملفات"); verify 0, 1, 2, 3, 10, 11, 100, 101; keep the numeral policy from finding 6 consistent inside the plural (digits and noun form must agree); cover `workbench_files_count`, `workbench_convert_files` and `workbench_conversion_summary` in one pass so the app never mixes fixed and plural forms.

## Fatal flaw

**The Arabic stops at the chrome.** The stated differentiator is Arabic quality beyond a machine-translated menu (`PRODUCT.md:21-22`), and the brand promise is trust in what the app does with your file. Every surface that describes what actually happened — the note on a converted file, the pack that makes Arabic OCR work, the privacy policy that backs the trust claim, the technical details behind a failure — is generated outside the resource system in English. The user is fluent in the app right up to the moment the app has something to tell them, and then the language changes under them. One screenshot of a converted Arabic scan would end the discussion; the repo cannot produce it, because `docs/qa/verification.md:141` records that no visual rendering was ever captured, and the whole 200-line verification document contains the words "Arabic", "RTL" and "locale" zero times.

## Questions the design team should answer

1. **What is the numeral policy — ٠١٢٣ or 0123 — and where is it written down?** Today `%d` localises and `Int.toString()` does not, so one card shows both (finding 6), and prose hand-types a Latin 50.
2. **Who owns the Arabic string file, and does that ownership cover generated strings?** The 218 translated keys are good; the four surfaces in findings 1, 2, 4 and 11 are untranslated and outside any review loop. Is a named native reviewer part of the release gate, or is parity count the gate?
3. **Is "Arabic only if the phone is Arabic" a decision or an omission?** No `localeConfig` and no switch (finding 10) is defensible for a closed test and indefensible for an Arabic-first launch — which is it?
4. **Is English-only engine detail an intentional contract?** `docs/qa/verification.md:166` says yes for details; `values-ar/strings_ui.xml:14` and `:16` contradict it by wrapping that English in Arabic labels that promise otherwise. Decide once and make the label honest.
5. **Is the model-pack catalogue data or code?** It is three English literals in `model/PackCatalog.kt:32-34` today; the upscale family was already dropped once (`PRODUCT.md:79`), so this list will change. Key it before it grows.
6. **Has anyone looked at this app in Arabic on a phone?** `docs/qa/device-checklist.md:21` (A5) exists with an empty result, and `docs/qa/verification.md:139-148` says visual rendering was not verifiable on the host. Every mirroring judgement in this report is a code reading; the typography and truncation findings need one rendered RTL screen to close.
