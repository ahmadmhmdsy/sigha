# Android Platform / Material 3 Conformance (seat: material-conformance)

**Scope.** Read-only static review of `MainActivity.kt`, `ui/**` (20 files), `AndroidManifest.xml`, `res/values/themes.xml`, `res/values/colors.xml`, launcher icon XML, and `app/build.gradle.kts`. No build, no install, no device run. Behaviour claims follow from Compose/Material3/Activity source semantics; anything computed rather than measured is marked. Paths in Evidence are relative to `app/src/main/java/com/sigha/converter/` unless they start with `app/` or `res/`, which are relative to `app/src/main/`.

## Verdict

This is Material 3 *inside the content box* and not Material at the window boundary. The components are stock, the icon family is consistent, RTL hygiene is good and both palettes are hand-tuned — but nine nested `Scaffold`s each declare the window to have zero insets, system-bar icon appearance is frozen at `onCreate` from the *system* theme rather than the app theme, and nothing consumes IME or safe-drawing insets. The three consequences are already visible in code: the Queue list slides under the nav bar when no job is active, the only text field can be typed under the keyboard, and a forced theme (a shipped setting) can make status/nav icons unreadable. The app is a solid Material 3 school exercise that skipped the platform's window contract.

## Strengths

1. **Stock Material 3 primitives, one icon family, real touch targets.** Every control is imported from `androidx.compose.material3` (`Scaffold`, `TopAppBar`, `NavigationBar`, `SnackbarHost`, `AlertDialog`, `FilterChip`, `RadioButton`, `Slider`, `OutlinedTextField`, `LinearProgressIndicator`; e.g. WorkbenchScreen.kt:36-52, SighaNavHost.kt:9-13) and every icon is `Icons.Outlined.*` or `Icons.AutoMirrored.*` — no third-party widget kit and no mixed icon sets. Because controls are M3 components, 48dp minimum touch targets, ripple and state layers come for free; the only bare `Modifier.clickable` sits on full-width rows.
2. **Correct edge-to-edge entry point and a genuinely designed dark palette.** `enableEdgeToEdge()` runs before `setContent` (MainActivity.kt:37), and dark mode is a real second palette with its own in/on/container colours and its own category accents (Theme.kt:36-55; FormatUi.kt:60-74), not an inversion of light. The theme mode is persisted and applied from one state read (MainActivity.kt:41-49), so light/dark/system switching works at the content layer.
3. **RTL and tab-state hygiene.** Zero `padding(left=…)`/`padding(right=…)` in `ui/` — all horizontal spacing uses `start/end`, `supportsRtl="true"` (AndroidManifest.xml:17), and directional arrows are `AutoMirrored` (Common.kt:16,73; HistoryScreen.kt:18,207). Tab switching uses `popUpTo(saveState) + restoreState` (SighaNavHost.kt:134-142), so per-tab scroll/back stacks survive; `NavigationBar` also consumes its own bottom inset correctly (SighaNavHost.kt:52).

## Qiyas card 1 — One window owner; every screen inherits its insets

- **Al-Far' (proposal):** Replace the nine nested `Scaffold`s and nine `WindowInsets(0,0,0,0)` overrides with one chrome owner at the `NavHost` (single Scaffold or `NavigationSuiteScaffold`) that consumes `WindowInsets.safeDrawing` + IME exactly once and passes resolved padding to screens; top bars stay per-screen via a slot; delete the ad-hoc `navigationBarsPadding()` calls.
- **Al-Asl (precedent):** Google's Now in Android (`android/nowinandroid`) — one `NiaApp` Scaffold owning navigation chrome and window insets, a chrome-free `NiaNavHost` receiving `PaddingValues`, every feature screen layout-only. Same shape as the Android "edge-to-edge in Compose" guidance.
- **Al-'Illa (causal invariant):** A window inset is a property of the window, not of a screen. It must be consumed exactly once at the highest composable that owns the system bar; descendants receive only resolved padding. Duplicating the decision across N owners gives N chances to zero it and N chances to drift — the Queue screen (#3) is the proof, not a prediction.
- **Conditions:** verify on 3-button nav in landscape (side insets), punch-hole/cutout top, gesture nav bottom, and with the IME open on the pages field; snackbar must clear both bars; route changes must not re-layout the chrome; no content may be clipped when the bottom bar is conditionally hidden.

## Qiyas card 2 — System chrome is a function of the app theme, not of boot time

- **Al-Far' (proposal):** Derive `SystemBarStyle` from the resolved `darkTheme`, re-apply it in a `SideEffect` on every theme change, and expose Material You behind an opt-in toggle with the brand palette as fallback.
- **Al-Asl (precedent):** The Material 3 / Now in Android pattern — `enableEdgeToEdge()` in the Activity, then appearance flags owned by the theme composable (`isAppearanceLightStatusBars/NavigationBars` re-derived from Compose state); Play Store and Google apps on Android 12+ follow wallpaper colour.
- **Al-'Illa (causal invariant):** Chrome is part of the theme's surface, not a launch constant. If any UI can diverge from system configuration (forced theme, scheduled dark mode, dynamic colour), bar appearance must be a pure function of the same state that drives content colour and be re-evaluated whenever that state changes.
- **Conditions:** status/nav icon contrast ≥3:1 for every (system theme x app theme) combination; appearance updates within one frame of a theme change; dynamic colour only on explicit opt-in, with the 26 fixed category accents contrast-checked against dynamic surfaces; a11y previews for both mismatch directions.

## Fatal flaw

The app is Material 3 everywhere inside the content box and not Material at the window boundary. Nine nested `Scaffold`s each declare the window to have no insets, system-bar appearance is frozen at `onCreate` from the *system* theme, and IME/cutout insets are consumed nowhere. That one architectural choice produces the Queue content sliding under the nav bar, the pages field under the keyboard and invisible status icons in the app's own forced-theme mode — and it guarantees the tenth screen gets it wrong too, because "how insets work here" is knowledge each screen must rediscover.

## Questions the design team should answer

1. Is Material You a deliberate "no" (brand-first) or an omission? If deliberate, write it into PRODUCT.md and own the contrast guarantee for the 26 fixed category accents.
2. Is tablet/foldable/large-screen in scope (Play large-screen eligibility)? If yes, is a rail at ≥600dp in 0.2.x or 1.0; if no, are we accepting that the bottom bar is the forever answer?
3. When the app theme differs from the system theme, should system bars follow the app (my recommendation) or the OS? Whoever owns this must own the contrast test matrix.
4. When a file is shared into Sigha while the user is on another tab, should the app jump to the Workbench (my recommendation) or drop an in-place "1 file added — Open" snackbar? Cold start vs `singleTop` warm start may differ.
5. Is the two-line top bar (app name + tagline) worth the 200% font-size clipping risk, or can the tagline live only in the Workbench empty state/About?
6. Notification permission: is first-Convert-with-rationale acceptable product/privacy messaging, instead of the first-launch system prompt?
7. Is "no animation" a deliberate utilitarian aesthetic or unfinished work? If deliberate, document it; if not, which transitions are in scope (tab switch, disclosure, dialog)?
