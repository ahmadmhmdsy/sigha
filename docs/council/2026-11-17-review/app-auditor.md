# Seat: The Engineer — app/platform architecture, data flow, and file-pipeline security

Project: **Sigha (صيغة)** — `E:\android_apps\digital_converter`
Review date: 2026-11-17. Scope: `app/src/main/java/com/sigha/converter/{core,data,ui,model,work}`, `AppGraph.kt`, `MainActivity.kt`, `SighaApp.kt`, `app/src/main/AndroidManifest.xml`, `app/src/main/res/**`.
No application sources were modified for this review. All evidence below is from files read in-repo or commands run in-session; web claims are marked unverified where noted.

## Verdict (one paragraph)

The architecture is unusually clean for a v0.1: a tiny manual DI graph, a pure data-first format registry, a stated converter-graph router, correct MediaStore scoping for API 29+, a genuinely hash-pinned model-pack installer, a 165/165 EN/AR string parity in Compose, and an honest test suite (131/131 green, actually executed). The pipeline's weak seam is **execution durability and failure/error surfacing**: conversions run only in a process-scoped `CoroutineScope` although `androidx.work` is declared (and its merged permissions/services are shipped), so backgrounding or process death destroys in-flight batches, and there is no foreground service or notification. Packaging also undercuts a headline claim: the APKs on disk store native libraries **compressed** with `android:extractNativeLibs="true"`, so the "16 KB-page aligned" claim is not established by `zipalign -P 16`, and the claimed APK size/hash does not match a fresh build in the tree. Error localization is incomplete in practice: 139 engine exceptions are hard-coded English and are shown verbatim in the queue and history. These are fixable without re-architecting; the core layering (core → data → work/ui, engines behind `Converter`) is sound and should be kept.

## Findings

### F1 — High — Long conversions have no durable execution: no Worker, no foreground service, no notification
- **Evidence:** `app/src/main/java/com/sigha/converter/data/AppCoroutines.kt:11` (`AppScope = CoroutineScope(SupervisorJob() + Dispatchers.IO)`); `app/src/main/java/com/sigha/converter/work/ConversionQueue.kt:83` (`activeJob = AppScope.launch { runBatch(...) }`); `app/build.gradle.kts:74` declares `androidx.work:work-runtime-ktx:2.10.0`, but `grep -R "WorkManager\|CoroutineWorker\|startForeground\|NotificationCompat\|NotificationManager" app/src/main/java` returns **0 matches**; `queue` rows are in-memory only (`ConversionQueue.kt:61-62`).
- **Why it matters:** A multi-minute ffmpeg video job or a large batch runs in a plain app-process coroutine. Swiping the app away, low-memory kill, or backgrounding on a busy device terminates the process: every un-finished queue row disappears, the half-written cache file is orphaned, and the user has no notification or progress outside the app. (The Lead's "WorkManager 10-minute limit" question is moot today because no work is ever enqueued.) The declared `POST_NOTIFICATIONS` permission is never requested, consistent with "no notification exists" — hiding a missing product feature behind a dead permission.
- **Fix:** Persist a job spec (URIs + target + options) in DataStore and run the batch through a `CoroutineWorker` (chunked under the 10-min limit, `setProgress` for UI) **or** an FGS with a progress notification and `POST_NOTIFICATIONS` runtime request on API 33+; make `ConversionQueue` an observer of durable state. If neither is planned for v0.1, remove `androidx.work` and state the limitation in-product.

### F2 — High — "16 KB-page aligned" is not established; both APKs ship compressed native libraries with `extractNativeLibs="true"`
- **Evidence:** `app/src/main/AndroidManifest.xml:12` sets `android:extractNativeLibs="true"` (merged manifest confirms it: `app/build/intermediates/merged_manifests/debug/processDebugManifest/AndroidManifest.xml:33`); `app/build.gradle.kts:47` sets `jniLibs { useLegacyPackaging = false }`. Command run:
  `& C:\Android\Sdk\build-tools\36.0.0\zipalign.exe -c -P 16 -v 4 .tmp_verify\app-debug-claimed.apk` → `EXIT=0`, but its output reports
  `22776375 lib/arm64-v8a/libavcodec.so (OK - compressed)`, `32709649 lib/arm64-v8a/libavdevice.so (OK - compressed)`, `lib/arm64-v8a/libc++_shared.so (OK - compressed)`; same for the current `app/build/outputs/apk/debug/app-debug.apk` (`lib/x86_64/libtesseract.so (OK - compressed)`).
  Compressed entries are not alignment-checked by zipalign, so "Verification successful" does **not** prove 16 KB page compatibility. Play's 16 KB page-size requirement for apps targeting Android 15+ expects native libs left uncompressed/aligned (Android docs `developer.android.com/guide/practices/page-sizes`; web claim **not fetched/verified** in this session because the web provider was unavailable — the local zipalign evidence stands on its own).
- **Why it matters:** This is the project's headline platform-readiness claim (docs/qa/verification.md). Explicit `extractNativeLibs="true"` defeats `useLegacyPackaging=false`; the libraries are compressed and extracted at install, which is the configuration Google's 16 KB guidance warns against, and it inflates the APK.
- **Fix:** Delete `android:extractNativeLibs` from the manifest (let AGP emit `false`), rebuild, and re-verify: `zipalign -c -P 16 -v 4 app-debug.apk` must list every `lib/*.so` as **uncompressed**. Then re-baseline size/SHA-256 in docs and correct the QA claim.

### F3 — High — Unused WorkManager dependency ships background permissions, services and receivers it never uses
- **Evidence:** `app/build.gradle.kts:74` (`work-runtime-ktx:2.10.0`); zero source references to WorkManager/Worker; merged manifest gains `WAKE_LOCK`, `RECEIVE_BOOT_COMPLETED`, `FOREGROUND_SERVICE` (`merged_manifests/.../AndroidManifest.xml:18-20`), `androidx.startup.InitializationProvider` with `WorkManagerInitializer` (`:74-90`), and `SystemAlarmService`, `SystemJobService`, `SystemForegroundService` plus constraint receivers (`:92-139`).
- **Why it matters:** For a privacy-first, fully-offline app, shipping wake-lock/boot-received/FGS permissions and three background services that are never used is a trust and store-review liability, and it adds startup/APK cost. It also makes the manifest's permission posture look inconsistent with the product promise.
- **Fix:** Remove `androidx.work` unless F1 is implemented with it; then keep only the permissions the worker actually needs. Regenerate and re-inspect the merged manifest as part of QA.

### F4 — High — 139 user-facing engine errors are hard-coded English and reach the UI/history verbatim
- **Evidence:** `grep -R 'ConversionException("' app/src/main/java` → **139** literal-English messages, e.g. `engine/archive/ArchiveIo.kt:24` "Not enough storage space to start the conversion.", `engine/pdf/PdfToTextConverter.kt:82` "This PDF is password-protected…", `engine/media/FfmpegRunner.kt:196` "The app no longer has access to this file…". Path to user: `data/ConversionRunner.kt:92-98` and `:132-138` pass `error.message` into `ConversionItemResult.errorMessage`; `work/ConversionQueue.kt:180-207` copies it to the queue row and to `HistoryEntry.error`; `ui/QueueScreen.kt:234-240` and `ui/HistoryScreen.kt:239-248` render it unchanged. `FfmpegRunner.kt:145-156` additionally appends the raw FFmpeg log tail to the message.
- **Why it matters:** The "full EN/AR strings" claim holds for UI chrome (165/165 parity, zero hard-coded Compose `Text`) but not for runtime errors: an Arabic user who hits a password-protected PDF reads English (plus technical ffmpeg log lines) in the queue, workbench progress and history. This is the most visible bilingual gap in the app.
- **Fix:** Replace string messages with typed failures (e.g., sealed `ConversionFailure(code, args)`) resolved to `R.string.*` at the UI boundary; keep the ffmpeg log tail only in a "details" affordance, or strip it from the primary message. Errors need both `values/` and `values-ar/` entries.

### F5 — Medium — Persisted SAF read grants accumulate forever and are never released
- **Evidence:** `data/IncomingFilesBus.kt:69-76` (`takePersistableUriPermission` for every share/view URI), `ui/WorkbenchViewModel.kt:96-101` (again for every picked file); `grep -R releasePersistableUriPermission app/src/main/java` → **0 matches**; history only stores the URI string (`data/HistoryCodec.kt:10-21`), so stale grants are never revoked when rows are evicted by the 50-entry cap or cleared.
- **Why it matters:** Android caps persisted URI grants per app (128). Each file the user shares/views/picks consumes one; once the cap is hit, `takePersistableUriPermission` throws (silently swallowed at `IncomingFilesBus.kt:72-76`) and older URIs — including history's "open" targets — can no longer be reopened after process death. This is a slow-leak UX failure on an app whose selling point is reopening converted files.
- **Fix:** Release grants when a file leaves the current selection and when a history entry is evicted/cleared (`releasePersistableUriPermission(uri, READ)`), and on open-failure prompt the user to re-pick the file instead of failing silently.

### F6 — Medium — DataStore corruption is not handled; one corrupt file can permanently break history writes and abort batches
- **Evidence:** `data/HistoryStore.kt:16` `preferencesDataStore(name = "sigha_history")` and `data/SettingsStore.kt:39` `preferencesDataStore(name = "sigha_settings")` — neither passes a `corruptionHandler`; reads use `.catch { emit(emptyPreferences()) }` (`HistoryStore.kt:23-26`) but writes do not: `record()` (`HistoryStore.kt:28-33`) calls `store.edit` and propagates `CorruptionException`; `work/ConversionQueue.kt:83-99` catches any `Exception` from `runBatch` and marks every unfinished row FAILED. The comment at `HistoryCodec.kt:23-26` claims corruption tolerance, but it only covers the JSON payload, not the DataStore file.
- **Why it matters:** A corrupted preferences file (partial write, killed process) turns every conversion attempt into a failed batch after the file is already published, and settings writes stop applying for the life of the install. The defensive intent exists but stops one layer too low.
- **Fix:** Pass `corruptionHandler = ReplaceFileCorruptionHandler { emptyPreferences() }` to both delegates, and wrap `HistoryStore.record/remove/clear` so a persistence failure never aborts a conversion batch (log + surface a non-blocking message).

### F7 — Medium — Model-pack download is composition-scoped (no resume) and its specific errors are discarded; progress state is mutated off-main
- **Evidence:** `ui/ModelPacksScreen.kt:78` starts the download in `rememberCoroutineScope()` — navigating back cancels the ~28 MB download; `:84-89` shows a generic `model_packs_download_failed` snackbar and drops `result.exceptionOrNull()` (so `PackInstaller.kt:194-203` "Not enough free space…", `:162` hash-mismatch message, and `:94` network failure text are never displayed). `ModelPacks.kt:84-92` invokes the progress callback on `Dispatchers.IO`; `ModelPacksScreen.kt:79-81` writes a Compose `mutableStateMapOf` from that callback → Snapshot-state mutation from a background thread.
- **Why it matters:** Users lose a 28 MB download by backing out of the screen, get an unhelpful "download failed" for actionable causes (disk full, hash mismatch, no network), and the off-thread snapshot write is a latent `ConcurrentModificationException`/inconsistent-UI risk.
- **Fix:** Run the download in a ViewModel/app scope (or `WorkManager` with a notification) with resumable `.part` handling; show `exceptionOrNull()?.message` localized; marshal progress through a `StateFlow<Float>` updated with `withContext(Dispatchers.Main)` or collect with `collectAsState`.

### F8 — Medium — Selections larger than 60 files silently lose queue rows while still converting
- **Evidence:** `work/ConversionQueue.kt:82` `_entries.update { current -> (batch + current).take(MAX_ENTRIES) }`, `MAX_ENTRIES = 60` (`:241`); `ui/WorkbenchViewModel.kt:161` passes **all** selected files to `queue.start`; the picker (`WorkbenchScreen.kt:109`, `:185`) has no count cap. `runBatch` then iterates the full batch and updates rows by id (`ConversionQueue.kt:127-131`) — rows dropped at enqueue never reappear.
- **Why it matters:** Pick 80 files, 20 conversions proceed invisibly: no progress row, no "open"/"share" affordance, and no error if they fail. It also worsens F1 (an 80-file batch is a multi-hour unprotected process).
- **Fix:** Cap the selection (e.g., 50) with a clear message, or make `MAX_ENTRIES` at least the batch size and only cap *finished* rows; add per-row retry for failures.

### F9 — Medium — Output-folder mode has no validation or fallback; a revoked/deleted folder fails every item
- **Evidence:** `work/ConversionQueue.kt:212-218` builds `PublishTarget.Folder` from the stored string with no `canWrite()` check; `data/OutputPublisher.kt:186-191` then throws `err_output_folder` per item; `ui/SettingsScreen.kt:83-98` only persists the pick, never re-validates, and there is no UI path to clear the folder or revert to Downloads on failure.
- **Why it matters:** Users who delete the chosen folder (or whose grant is lost after backup/restore) get a batch where every file fails with a generic message, with no recovery path visible in the app.
- **Fix:** Validate the tree at batch start (`DocumentFile.canWrite`); on failure fall back to Downloads with a snackbar or prompt "choose folder again"; add a "reset to Downloads" action in Settings.

### F10 — Medium — No disk-space preflight on the media pipeline even though it copies the whole input into cache
- **Evidence:** `engine/media/FfmpegRunner.kt:158-189` copies the selected file into `cacheDir` before conversion (a 4 GB video needs ≥4 GB free, plus output), with no free-space check; `data/OutputPublisher.kt:64-83` does not check either. Checks exist only for PDF (`engine/pdf/PdfSupport.kt:28-33`) and archive (`engine/archive/ArchiveIo.kt:23-24`).
- **Why it matters:** On a nearly-full device the app starts a long copy, fails halfway with a generic English error (F4), and can fill the user's storage with orphaned cache files — a common complaint class for converter apps and a review risk.
- **Fix:** Add one shared preflight in `ConversionRunner.convert` (before each step: input size + estimated output + margin, via `StatFs`/cache dir `usableSpace`) and fail early with a localized, actionable message; also preflight in `OutputPublisher`.

### F11 — Medium — Legacy (API 26–28) publish can report failure after the file was successfully written
- **Evidence:** `data/OutputPublisher.kt:148-172` writes the file into `Download/Sigha`, then `scanIntoMediaStore` (`:163-164`, `:174-184`) returns null on a 20 s timeout and the code throws `err_save_failed`. The delete-cleanup catch only wraps the copy (`:155-162`), not the scan, so the file stays on disk while `ConversionQueue.kt:179-207` records a failed history entry.
- **Why it matters:** On devices where `MediaScannerConnection` is slow or callback-less (MTP/OEM quirks), the user is told the conversion failed although the file exists in Downloads; retrying produces duplicates. The same false-negative can occur for the scanner returning null for a file it cannot index.
- **Fix:** After a successful write, treat scan failure as non-fatal: return the `file://` URI (or a `DocumentsContract`-free content fallback) with a "saved, gallery not updated" note, or delete the destination on failure; never mark the conversion failed once bytes are safely on disk.

### F12 — Low — Cancellation is cosmetic for the publish phase
- **Evidence:** `work/ConversionQueue.kt:104-107` marks rows CANCELLED synchronously while the job may still be publishing; `data/ConversionRunner.kt:112-121` publishes all final files after the last `ensureActive()` (`:112`), and publish/copy loops contain no cancellation checks (`OutputPublisher.kt:101-103`, `:156-158`).
- **Why it matters:** A user who cancels a large copy can still get the file in Downloads minutes later, while the row says CANCELLED and history has no record — an orphan output and a confusing state.
- **Fix:** Check cancellation inside the publish loop and stream copies; on cancel delete any partially published row/file; only record history for outputs you keep.

### F13 — Low — Edge-to-edge inset handling is inconsistent on sub-screens
- **Evidence:** All Scaffolds set `contentWindowInsets = WindowInsets(0, 0, 0, 0)` (e.g. `ui/QueueScreen.kt:118`, `ui/SettingsScreen.kt:103`), and `ui/SettingsScreen.kt:105-111` / `ui/QueueScreen.kt:135-140` add only fixed bottom padding (24–28 dp) with no `navigationBarsPadding()`; `ui/ModelPacksScreen.kt:113-118` does apply it. Sub-screens hide the bottom navigation bar (`ui/SighaNavHost.kt:44`), so nothing else consumes the nav-bar inset there.
- **Why it matters:** On gesture-nav devices the last list item/action on Settings, Queue and About/Licenses can sit under the system navigation bar — a visible polish/accessibility defect that undermines the otherwise careful responsive UI.
- **Fix:** Use `WindowInsets.safeDrawing` as Scaffold insets (or add `navigationBarsPadding()` to each sub-screen root) and verify on a gesture-nav emulator.

### F14 — Low — Broad exported intent surface: every MIME, every scheme, with no payload validation
- **Evidence:** `app/src/main/AndroidManifest.xml:30-44` exports `MainActivity` for `SEND`, `SEND_MULTIPLE` and `VIEW` with only `<data android:mimeType="*/*"/>` and no scheme/authority restriction; `MainActivity.kt:54-59` forwards every URI to `IncomingFilesBus`; `ui/WorkbenchViewModel.kt:92` only checks `scheme != null`, and `FormatRegistry.detect` (`core/FormatRegistry.kt:54-83`) is exception-tolerant.
- **Why it matters:** Sigha appears as an "open with" target for every file type on the device (including unrelated ones), which is poor UX and a Play/store-quality flag; any app can push arbitrary URIs into the workbench. I found **no** privilege escalation or crash path (detection wraps provider calls in try/catch and unsupported formats are dropped), so severity stays Low — but the ingress is under-validated.
- **Fix:** Split filters into the supported MIME families (image/*, application/pdf, audio/*, video/*, text/*, application/zip, …), add the specific schemes you accept, and reject/report unreadable payloads per file instead of silently dropping them.

### F15 — Low — Test suite covers pure utilities only; no tests for queue/runner/publisher/stores/installer and no instrumented tests
- **Evidence:** `app/src/test/java/...` contains 15 suites (RoutePlanner, HistoryCodec, UniqueNames, PdfPageSelection, ArchiveGuards, Csv, JsonCsv, FfmpegArgs, SubtitleFormat, HtmlTextExtractor, MarkdownParser, Digest, OcrLanguages, OcrPageRange, PackCatalog) — no tests for `ConversionQueue`, `ConversionRunner`, `OutputPublisher`, `HistoryStore`, `SettingsStore`, `PackInstaller`, `IncomingFilesBus`, `WorkbenchViewModel`; there is **no** `app/src/androidTest` directory at all.
- **Why it matters:** The riskiest code (durability, cancellation, SAF, MediaStore, state machines) is exactly what is untested; the 131 green tests give false confidence about pipeline correctness. Concrete/global seams (`AppGraph`/`Repo`, `OutputPublisher(context)`) make the pipeline hard to fake in JVM tests.
- **Fix:** Introduce narrow interfaces for publisher/history/settings, add coroutine tests for the queue (success, failure isolation, cancellation, >60 batch) with `kotlinx-coroutines-test`, and add instrumented/emulator tests for MediaStore on API 28/29/33 and SAF permission/revocation paths.

### F16 — Low — Global mutable singletons couple the pipeline and defy testability
- **Evidence:** `AppGraph.kt:13-33` (`object` with `lateinit var app/formats/registry`, `planner by lazy`), `data/Repo.kt:10-17` (lazy singletons built from `AppGraph.app`), `model/ModelPacks.kt:36-45` (`@Volatile` global context). ViewModels/queue reach them directly (e.g. `WorkbenchViewModel.kt:63-65`), so unit tests must initialise the whole graph and Android `Context`.
- **Why it matters:** This is what blocks F15 from being cheaply fixable; it also makes lifecycle order (Application.onCreate vs. any early access) fragile.
- **Fix:** Keep the manual-DI style but inject an `AppServices` interface (formats, registry, queue, history, settings, publisher) into ViewModels/queue constructors; the `AppGraph` object can remain the composition root that builds the production instance.

## Top-5 prioritized actions

1. **Make execution durable and visible (F1/F3/F7).** Choose one: `CoroutineWorker` + persisted job spec + progress notifications, or FGS for media jobs. Either way request `POST_NOTIFICATIONS` at first conversion on API 33+, remove the unused WorkManager dependency/permissions if you keep the coroutine path, and show conversion progress in a notification while backgrounded.
2. **Fix the packaging claim before any release (F2/F7-claim).** Remove `android:extractNativeLibs="true"`, rebuild, verify `zipalign -c -P 16 -v 4` shows uncompressed `lib/*.so`, re-baseline size + SHA-256, and correct `docs/qa/verification.md`; a claim that fails its own verification method is worse than no claim.
3. **Localize the error boundary (F4).** Convert the 139 English engine messages to typed failures/resource IDs resolved at the UI layer, keep ffmpeg log tails out of the primary message, and add Arabic translations; then the EN/AR claim becomes true end-to-end.
4. **Harden persistence and lifecycle boundaries (F5/F6/F8/F9).** DataStore corruption handlers, release persisted grants as history/selection churns, cap selections (or grow queue rows), validate the output folder at batch start with a Downloads fallback.
5. **Make the pipeline testable and tested (F15/F16).** Introduce interfaces for publisher/history/settings and an injectable services container; add coroutine tests for queue success/failure/cancel/>60 and instrumented tests for MediaStore + SAF on API 28/29/33 — that is where this app's real regression risk lives.

## Verified strengths (only what I actually checked)

- **Clean dependency direction and small composition root:** `core` (formats/Converter/route planner) has no Android UI or storage imports; `data`/work depend on core; `ui` depends on both. Engines implement one edge behind a `Converter` interface (`core/Converter.kt:43-48`). Manual DI (`AppGraph.kt`) with lazy singletons keeps cold start cheap and is readable.
- **Correct scoped-storage publishing for API 29+:** `RELATIVE_PATH`, `IS_PENDING`, unique display names, delete-on-failure and a proper `MediaStore.Downloads` collection (`OutputPublisher.kt:86-118`); the legacy path is clearly separated and permission-gated (`:139-172`).
- **Genuine supply-chain discipline for model packs:** hard-coded commit-pinned HTTPS URLs, per-file SHA-256, size-enforced streams, bounded redirects, timeouts, `.part` cleanup, free-space check and replace-only-after-verify (`PackCatalog.kt`, `PackInstaller.kt`). No code or catalog-driven path is ever downloaded.
- **Defensive format detection and RTL/i18n UI:** `FormatRegistry.detect` degrades gracefully on provider failures; 165/165 EN/AR string parity with no hard-coded Compose text; `AutoMirrored` back/forward icons; `supportsRtl="true"`; `allowBackup="false"`; converted files are private until published.
- **Bounded, cancellable native work:** FFmpeg input copy checks cancellation per chunk and cleans temp files on failure (`FfmpegRunner.kt:191-218`); `ConversionRunner` keeps every intermediate in `cacheDir` and deletes it in `finally` (`:146-148`), pruning stale dirs (`:165-176`).
- **Tests that actually run:** 131/131 green in 15 JVM suites (executed with `--no-build-cache`; parsed from XML), and the test suite is honest about being JVM-only.

## Notes / limitations of this review

- No device or emulator was used (`adb`/hardware paths not exercised); Android API 26–28 publish behavior, SAF revocation, notification permission flows and OEM provider quirks are code-reviewed only.
- `zipalign` evidence is from the APKs currently on disk; I did not rebuild the APK to re-baseline after F2's fix.
- Web provider was unavailable, so the Play 16 KB requirement URL is cited but not fetched/verified; the local compression evidence is independent of it.
- The 32-edge converter graph, engine correctness, model licensing and legal claims are other seats' scope and were not re-derived here.
