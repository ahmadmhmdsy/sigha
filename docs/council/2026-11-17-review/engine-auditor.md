# Seat: The Engineer — engines and routing (qiyas tool: al-Far', the branch)

Auditor: engine-auditor. Date: 2026-11-17 (Asia/Baghdad). Workspace: E:\android_apps\digital_converter
Scope: all 51 files under app/src/main/java/com/sigha/converter/engine/, all 5 files under core/, plus read-only cross-checks into data/ConversionRunner.kt, data/ConversionQueue.kt, data/AppCoroutines.kt, ui/WorkbenchViewModel.kt, res/values/strings.xml, and the docs that make claims about them. Every engine file was read (not sampled). Counts below were derived from the source (grep/count of declarations and declared input/output sets), not from documentation.

Not run in this seat: :app:testDebugUnitTest, any build, any emulator/device conversion, any FFmpeg/Tesseract/PDFBox/MediaStore execution. Runtime statements are code-path inferences from reading, and are marked as such where they matter. This seat created no source change; this report is its only artifact.

## Verdict (one paragraph)

The engine layer is the best-built part of Sigha: a small, honest converter graph with a correct uniform-cost router, format-agnostic converters, pure testable helpers, and real safety work (nothing is ever extracted to disk, so zip-slip is structurally impossible; XXE is disabled; passwords, OOM, cancellation and temp files are mostly handled with visible care). The failures are at the integration seams, not in the leaves: converter disclosure notes are computed and then thrown away; one equal-cost duplicate edge silently shadows the OCR PDF converter that the product sells as its AI feature; multi-output intermediate steps drop every file but the first; the PDF page range is honoured for rasterising but ignored for text extraction; FFmpeg has no execution timeout; media metadata is copied instead of stripped in a privacy-first app; and error containment stops at Exception, so an OOM in the text/office/ebook/archive paths is an app crash rather than a failed item. Two catalogue claims are demonstrably false ("every format has a working edge"; "resize"), and "32 converter edges" undercounts the actual routing graph five-fold (172 edges, 171 distinct pairs; 32 is the number of converter implementations). None of this is architectural rot — the seams are thin and fixable — but three of these defects are user-visible data loss or a privacy leak, and two are hard reliability failures.

## Findings

### F1 — High — Converter notes are produced everywhere and displayed nowhere; every fidelity limit is silent
**Evidence.** ConversionResult carries note (app/src/main/java/com/sigha/converter/core/Converter.kt:34). At least 12 producers set it: media/VideoConverter.kt:46,60,63 (GIF 30-second cap, software-encoder fallback), office/OfficeConverters.kt:214,295-300 (tables/images flattened, first worksheet only), office/WorkbookReader.kt:11 (dates as serials), archive/ArchiveConverters.kt:211,442 (skipped duplicates/symlinks), ebook/EbookConverters.kt:40,69 (styling/images omitted), pdf/PdfToTextConverter.kt:64-69 (no selectable text), ocr/OcrFiles.kt:14,25 and ocr/PdfTextConverter.kt:54,74 (page window), text/TextConverters.kt:44-49 (line cap). No consumer exists: data/ConversionRunner.kt:88-108 uses only outputs; data/ConversionModels.kt:15 has no note field; work/ConversionQueue.kt:148-178 records only the primary file; ui/WorkbenchViewModel.kt never reads a note. A grep for note in data/ and ui/ returns only unrelated string resources. docs/models/integration.md:140 claims "the result note says 'Only the first 50 of N pages were read.'" — it cannot, because the note never leaves the engine.
**Why it matters.** Every silent loss the engine carefully avoids hiding is in fact hidden: a 4-hour video becomes a 30-second GIF with no indication; a 3-sheet workbook becomes one sheet; DOCX tables and images disappear; a scanned PDF reports a generic failure; OCR of a 300-page PDF quietly reads 50 pages. This is the single cheapest trust fix in the codebase.
**Fix.** Add note (or notes: List) to ConversionItemResult, carry it through ConversionQueue/QueueEntry, show it in the progress row and history detail. Merge multiple step notes with "; ". Because notes are hardcoded English, route them through resources at display time or keep them as secondary detail text until localized (see app-auditor F4).

### F2 — High — Scanned PDF → TXT is a guaranteed failure; the OCR fallback is registered but unreachable
**Evidence.** BuiltInConverters.kt:25-35 registers image, pdf, office, text, data, subtitle, ebook, media, ocr, archive, upscale in that order, and the registry emits every declared edge in that order (core/ConverterRegistry.kt:12-20). pdf/PdfConverters.kt:7-10 registers PdfToTextConverter (PDFBox) before ocr/OcrConverters.kt:25-28 registers PdfTextConverter (OCR). RoutePlanner relaxes only on strict improvement (core/RoutePlanner.kt:30), so the second equal-cost pdf→txt edge is never taken; the OCR converter is unreachable through the planner. PDFBox's converter then writes a 0-byte file with a note (pdf/PdfToTextConverter.kt:62-69); ConversionRunner filters outputs to isFile && length > 0 (data/ConversionRunner.kt:89), finds nothing, and throws err_empty_output (data/ConversionRunner.kt:100-105; strings.xml:186 "The converter returned no file."), so even the explanatory note is lost. Product docs acknowledge the shadowing but not the note loss (docs/models/integration.md:156-166, docs/qa/verification.md:118-120, docs/product/PRODUCT.md:70).
**Why it matters.** "OCR fallback" is a headline feature; scanning a paper document to text is a core use case. Today it fails 100% of the time from the normal picker, while a fully written 175-line OCR PDF converter (with page windows, caps and tests) sits dead in the graph.
**Fix (one Lead-owned file).** In pdf/PdfToTextConverter.kt, after writeText, if the extracted text is blank, delegate to ocr/PdfTextConverter with the same request and return its result; keep the existing note path for the empty case as a fallback. Do not reorder OCR before PDFBox (digital PDFs would lose layout and pay OCR cost). Add a test for the blank-text branch seam.

### F3 — High — A multi-output intermediate step silently drops every file except the first (PDF → WebP loses all pages after 1)
**Evidence.** ConversionRunner keeps one URI forward: finalFiles = outputs; currentUri = Uri.fromFile(outputs.first()) (data/ConversionRunner.kt:106-108), and publishes only the final step's outputs (:113-120). PdfToImageConverter returns one file per selected page (pdf/PdfToImageConverter.kt:82-117). A PDF → WebP request is routed pdf→png (multi-page) then png→webp (ImageToImageConverter), so the runner converts page 1 to WebP and discards the other page files; no note is attached (and notes are dropped anyway, F1). The UI offers WebP as a target for PDF input because reachableTargets(pdf, 3) includes it (ui/WorkbenchViewModel.kt:244-260). Mutatis mutandis any future multi-output converter used as a non-final step has the same defect.
**Why it matters.** Silent data loss in a shipped conversion route; a 40-page scan becomes a 1-page WebP that the user believes is the whole document. This also interacts with F1: a note would only half-solve it, because other pages are genuinely not converted.
**Fix.** Two options, both small: (a) in ConversionRunner, when an intermediate step yields N>1 outputs, run the remaining suffix route for each output and merge the final outputs (page-level fan-out); or (b) forbid multi-output converters as non-final steps in the planner/runner with a clear error, and until (a) lands, route PDF→WebP as an explicit "one file per page" multi-output conversion. Also attach a note naming the file count.

### F4 — High — PDF → TXT ignores the requested page range; PDF → PNG/JPG honours it
**Evidence.** pdf/PdfToTextConverter.kt:91-116 loops all pages from 1 to pageCount and never reads request.options.pages; only Parsed page ranges exist in pdf/PdfPageSelection.kt and are used solely by pdf/PdfToImageConverter.kt:82,128-130. The UI shows the Pages field whenever any selected file is a PDF, whatever the target (ui/WorkbenchViewModel.kt:222,231), and docs promise pages handling for PDF OCR (docs/models/integration.md:139-143). ConversionOptions.pages is defined at core/Converter.kt:10.
**Why it matters.** A user who asks for "pages 2-3" gets the whole document — wrong output that looks right, with no warning. It is also the exact opposite of the adjacent PDF→image behaviour, so it reads as a bug, not a limitation.
**Fix.** Parse spans with PdfPageSelection and iterate only the resolved indices, setting stripper.startPage/endPage per page (the loop already runs per page, so this is a 5-line change). Add a JVM test on the page-selection helper for the text path if it is extracted, or an instrumented test.

### F5 — High — No execution timeout in the media pipeline; one stuck FFmpeg session blocks the whole queue forever
**Evidence.** media/FfmpegRunner.kt:80-128 starts FFmpegKit asynchronously and suspends on completion.await() (:113) with no withTimeout; the only watchdog cancels the native session when the user cancels and is otherwise inert (:102-110). A grep for withTimeout in the engine tree returns zero hits. withMedia cleanup (:63-77) runs only after the suspend resumes, so the cache input copy survives a hung session until the 6-hour stale prune (:242-247). The queue is strictly sequential (work/ConversionQueue.kt:127-131, one active job), so a hung ffmpeg freezes every following file. Separately, the input is copied to cache with no size cap (:191-218) — app-auditor F10 covers the missing disk preflight; the unbounded copy is the engine side of it.
**Why it matters.** Native decoders hang on damaged/live-recorded media, and there is no user-visible recovery: the app shows "running" forever and cancellation of the coroutine does not stop the native session unless the poll happens. A 20 GB video also gets copied twice before anything fails.
**Fix.** Wrap completion.await() in withTimeout(budget) with a budget derived from probe duration/size (e.g. max(60s, 4x duration)); on timeout call FFmpegKit.cancel(session.sessionId) and throw a friendly "This media took too long to convert" ConversionException so the queue item fails and cleanup runs. Add a MAX_INPUT_BYTES check against free cache space before copyInput.

### F6 — High — Converted media keeps the source metadata (privacy defect in a privacy-first product)
**Evidence.** engine/media/FfmpegArgs.kt constructs every audio/video command explicitly (-y, codecs, containers, filters) but never adds -map_metadata -1 (or -map_chapters -1); grep -R "map_metadata|map_chapters" over app/src/main/java returns 0 hits. FFmpeg's default is to copy global metadata to the output container, so GPS location, creation date, camera model, author and comment survive a video→mp4/webm/mkv or video→audio conversion. Images are safe by construction: re-encoding through Bitmap.compress (image/ImageToImageConverter.kt:87-91) drops EXIF; PDF/office/EPUB outputs are generated from scratch. docs/product/PRODUCT.md:22 promises only "EXIF fix" for images and does not claim media sanitising, but README.md:3,5 and strings.xml:6 sell privacy ("Nothing is uploaded", "privacy-first").
**Why it matters.** Offline privacy and metadata privacy are different promises; a user who trims a phone video and shares it has now shared where and when it was filmed, stamped by the app that markets privacy. This is a one-line fix with a test, and its absence in a reviewed codebase is a red flag for a privacy claim.
**Fix.** Append -map_metadata -1 -map_chapters -1 to every audio/video argument list (all rate-control paths and the software fallback share the same builders); add assertions to engine/media/FfmpegArgsTest.kt (it already asserts the absence of GPL encoders, so the pattern exists). Document "metadata is stripped" in PRODUCT/README only after the test lands.

### F7 — High — An OutOfMemoryError in text/office/ebook/data/archive engines is not contained; it crashes the app instead of failing the item
**Evidence.** data/ConversionRunner.kt:130-145 catches CancellationException, ConversionException and Exception, never Error. work/ConversionQueue.kt:84-98 does the same. data/AppCoroutines.kt:11 creates CoroutineScope(SupervisorJob() + Dispatchers.IO) with no CoroutineExceptionHandler, so an uncaught Error in the batch coroutine reaches the default uncaught-exception handler and the process dies. OOM is only caught inside image/pdf/ocr (grep for catch (e: OutOfMemoryError) finds ImageDecoding.kt:137, ImageToImageConverter.kt:33, ImageToPdfConverter.kt:38, PdfToImageConverter.kt:46, PdfToTextConverter.kt:44, PdfTextConverter.kt:142, BitmapLoader.kt:40,141). The unguarded paths are exactly the ones with the most allocatable work: JSON→CSV parses the entire (up to 24 MB) document into a tree (data/JsonCsv.kt:58-70), EPUB accumulates 2,000 chapters of up to 16 MB each into lists and then one joined String (ebook/EpubReader.kt:34-35,83-101; ebook/EbookConverters.kt:33-66), SafePackage permits 2 GB of declared expansion (office/OoxmlPackage.kt:88-90), XLSX reading allows 1,000,000 rows and 16,384 columns (office/WorkbookReader.kt), archive converters buffer through commons-compress.
**Why it matters.** A low-memory device converting a large but legal EPUB/JSON/DOCX gets an Android force-close instead of a red row and a friendly message. This is the worst failure class for a queue app: it loses the whole batch and the user's trust.
**Fix.** At the conversion boundary, catch Throwable, rethrow CancellationException, and map OutOfMemoryError to a ConversionException ("Not enough memory for this file; try a smaller file or split it"). Do that in ConversionRunner (single place) and keep the existing per-engine OOM catches where they exist. In parallel, add cumulative output caps for text-producing engines (e.g. 64 MB accumulated text in EPUB/office/JSON) to make OOM less reachable.

### F8 — Medium — "32 converter edges from 12 engine families" is not an edge count and the family count is wrong
**Evidence.** README.md:32 and docs/product/PRODUCT.md:59/verification.md:84 say 32 converter edges from 12 engine families. The code contains exactly 32 Converter implementations / ids (2 image, 2 pdf, 10 office, 3 text, 4 data, 2 subtitle, 2 ebook, 2 media, 2 OCR, 3 archive, 0 upscale; verified by count of override val id declarations). Because ConverterRegistry.register takes the cartesian product of each converter's declared inputs × outputs and skips identities (core/ConverterRegistry.kt:14-19), those 32 converters produce 172 directed format→format edges, 171 distinct pairs, because pdf→txt is registered twice (PDFBox + OCR). Arithmetic: image 7x3-3=18, image→pdf 7, pdf→image 2, pdf→text 1, office 10, text 3, data 4, subtitle 2, ebook 2, audio 14x7-7=91, video 6x4-2=22, OCR image 6, OCR pdf 1, archive 3 = 172. build-verifier F5 already found the "12 families" half (11 packages, 10 productive); this finding adds that the "32 edges" is also a mislabel.
**Why it matters.** The metric is used in the README and product doc to convey graph size; the real functional surface (which routes exist, where duplicates shadow) is invisible if you believe there are 32 edges. That is exactly why the duplicated pdf→txt edge and the dead formats survived review.
**Fix.** State "32 converters over 172 routing edges (171 format pairs, 11 engine families, 10 productive)" and keep it in one place. Add a JVM topology test (FormatRegistry + ConverterRegistry with null Android deps) asserting these counts and that no (from,to) pair has two converters — that test would have flagged both F2 and this mislabel.

### F9 — Medium — Nine of the 48 catalogue formats have no edge at all; the docs claim the opposite
**Evidence.** core/FormatRegistry.kt:90-148 lists 48 formats. Union of all converter input sets covers 39 of them; tiff, rtf, tar, bz2, xz, yaml, xml, mobi and fb2 appear in no converter inputs (tiff is additionally missing from engine/image/ImageFormats.kt:21; archive converters only read zip, 7z and gz). 23 of the 48 are never produced as a target either. docs/product/PRODUCT.md:66 says "Format count is 48, not ~270: every format here has a working edge; no catalogue padding." docs/qa/verification.md:127 admits only RTF/TIFF/DOC (and DOC is not even in the catalogue). build-verifier F6 separately covers the dead .doc/.xls MIME aliases; this is the catalogue side.
**Why it matters.** A user who picks a TIFF, MOBI, YAML or XZ file sees it recognised (correct name and category) then, after target selection, an empty target list or "This conversion isn't supported yet" — the catalogue advertises support it does not have. The claim in the product doc is exactly the kind of statement a reviewer will check.
**Fix.** Pick one: add the missing edges (TIFF input is nearly free once ImageFormats.inputs includes it; XML/YAML→CSV/JSON are moderate; MOBI/FB2/TAR/BZ2/XZ are real work) or mark formats as "known but not convertible" in the data model, hide them from source/target pickers, and rewrite the claim honestly ("48 recognised, 39 convertible"). Do not leave the false sentence.

### F10 — Medium — The ZIP entry guard runs after the full entry list is materialised
**Evidence.** archive/ArchiveConverters.kt:61-63 calls zip.entries().toList() and only then checkZipEntries(entries) (:78-95). Compare office/OoxmlPackage.kt:99-115, which counts entries lazily inside the Enumeration loop. The size guard (:82-93) sums only declared sizes, so unknown-size entries (spilled to a temp file, :136-175) contribute zero to the total; per-entry the spill is capped at 2 GB by copyFully (:432-434), but there is no aggregate cap over many unknown-size entries. On failure after the output has been opened, the partially written .tar.gz is left in place (:73-75 only deletes the temp input); in the app ConversionRunner's finally removes the whole work directory (data/ConversionRunner.kt:147), so this is an engine-contract wart rather than an app leak.
**Why it matters.** A crafted 5-million-entry ZIP allocates the entry list before the 50,000 limit can reject it (the central directory itself is also parsed eagerly by ZipFile), which is a cheap memory DoS on a privacy/offline tool that explicitly invites untrusted archives. The zip-slip protection itself is sound because nothing is extracted (see strengths).
**Fix.** Iterate zip.entries() with a counter and stop at MAX_ENTRIES before collecting; track total bytes written for all entries including the unknown-size spill; delete request.outputFile on failure inside the converter as well (belt and braces with the runner).

### F11 — Medium — EPUB: DRM is not detected, content accumulation is unbounded, and silent spine skips lose chapters
**Evidence.** ebook/EpubReader.kt:37-105 parses META-INF/container.xml, the OPF manifest/spine and each XHTML chapter, but never opens META-INF/encryption.xml or reads rights information (grep for encryption.xml in the engine returns 0 hits); an Adobe ADEPT or Readium LCP encrypted spine item is just bytes, so it yields garbage text or "No readable text was found in the book" — the app never says "DRM-protected". Chapter texts are accumulated in a list (up to 2,000 chapters x 16 MB) and then joined into one String in ebook/EbookConverters.kt:35; the HTML path builds one giant String too (:55-64). Spine entries missing from the manifest are silently skipped with ?: continue (EpubReader.kt:87-88), and chapters with no extracted text are dropped (:92) with only the "No readable text" total failure at the end.
**Why it matters.** Library EPUBs are frequently DRM-protected; today the user gets an empty/failed conversion with a misleading reason. And the unbounded accumulation is one of the concrete OOM paths behind F7.
**Fix.** Before reading chapters, detect META-INF/encryption.xml (and rights.xml for LCP) and fail with "This e-book is protected by DRM and cannot be converted." Cap cumulative chapter text (e.g. 64 MB) with a note; count skipped spine items/empty chapters and put that count in the note (once F1 lands).

### F12 — Medium — "Resize" is claimed but unreachable; dpi/maxDimension/trim are dead options; full-resolution decode is the only path
**Evidence.** docs/product/PRODUCT.md:22 promises "resize, quality, EXIF fix". ConversionOptions.maxDimension, dpi, startMs and endMs exist (core/Converter.kt:9-11) but no UI code sets them: the only option plumbing is quality, bitrate and pages (ui/WorkbenchViewModel.kt:139-149; WorkbenchScreen passes exactly those three at :269-271). ImageToImageConverter passes maxDimension straight from options (image/ImageToImageConverter.kt:53), so it is always null. ImageDecoding.decodeWithBitmapFactory checks MAX_PIXELS = 100,000,000 (image/ImageDecoding.kt:31,69) and only subsamples when maxDimension is set (:72,192-198): a 100 MP JPEG is a ~400 MB ARGB_8888 allocation attempt. The OOM path tells the user "Try a smaller maximum dimension" (image/ImageToImageConverter.kt:33-37) — a control that does not exist. The same mismatch exists for PDF: dpi is always the default 150 (pdf/PdfToImageConverter.kt:60) while the OOM message says "Try a lower DPI" (:47). PdfToImageConverter also has no max-pixel guard before Bitmap.createBitmap (:90-92) for a crafted huge MediaBox. Trim (startMs/endMs) is implemented and tested in FfmpegArgs but no screen exposes it.
**Why it matters.** The most useful image operation (shrink before sharing) is advertised and unavailable; large phone photos and 50 MP RAW-ish images fail instead of being downscaled; error messages point at non-existent settings; PDF renders are always 150 dpi with no way to raise or lower.
**Fix.** Either expose the four options (Resize long edge, PDF DPI, trim start/end) in the workbench for the relevant categories, or set safe defaults in the engines when options are null (images: maxDimension 4096; PDF: keep 150) and fix the messages. Add the PdfToImage max-pixel guard (e.g. reject > 80 MP after scaling) so a crafted PDF fails before allocation. This is UI+engine work but the dead options are already plumbed.

### F13 — Medium — The JVM suite does not test the parts this audit found defects in
**Evidence.** 15 test classes, 131 @Test (count matches docs/qa/verification.md:58 and build-verifier's run). There is no test for ConverterRegistry/FormatRegistry at all: nothing asserts edge counts, unique pairs, reachability, duplicate edges, dead formats or reachableTargets self-inclusion (RoutePlannerTest uses a fake 1-3 edge registry and never exercises the real catalogue; app/src/test/java/com/sigha/converter/core/RoutePlannerTest.kt:9-59). No test for archive converters (ArchiveGuardsTest tests name normalisation only), EpubReader, TextIo charset behaviour, PdfToTextConverter page handling (PdfPageSelectionTest tests the pure parser, not the converter), ConversionRunner's multi-output and note handling, or media runner timeout/cancel/cleanup. docs/qa/verification.md:78-79 states the coverage is logic-only. app-auditor F15 covers the wider test gap; this is the engine-specific list.
**Why it matters.** The two worst genuine bugs found here (F2 scanned PDF, F3 multi-output drop) and the false metric F8 are all one small JVM test away from being caught; the suite is green while the graph has a dead duplicate edge and nine dead formats.
**Fix.** Add a pure-JVM topology test over the real FormatRegistry + ConverterRegistry (no Android classes needed for count/duplicate/reachability assertions), plus a PdfToText page-span test by extracting the page iteration into a pure function, and Robolectric/instrumented tests for the archive/media/EPUB paths when instrumentation exists. Make the topology test part of the definition of done for any new edge.

### F14 — Medium — Legacy non-Arabic encodings are silently mis-decoded to ISO-8859-1 mojibake
**Evidence.** text/TextIo.kt:58-79 decodes BOM-prefixed UTF-8/UTF-16, then strict UTF-8, then Windows-1256 only when looksLikeLegacyArabic(bytes), else ISO-8859-1. A GBK (Chinese), Shift-JIS (Japanese), CP1251 (Russian) or CP949 (Korean) TXT file without BOM is therefore read as Latin-1 and produces mojibake in every downstream text conversion (TXT/MD/HTML→PDF, TXT→TXT-family CSV pipelines, OCR output comparison). There is no user encoding override (ConversionOptions.extra exists but is never used for this). The Arabic-first heuristic is sensible for the current market but is silently a product-wide limitation, and docs do not state it.
**Why it matters.** The app's 48-format catalogue and offline positioning invite international files; a user converting a Chinese txt to PDF gets garbage with no error. This is cheap to improve and cheap to disclose.
**Fix.** Add a small encoding detector (juniversalchardet is Apache-2.0, ~200 KB) or a heuristic for GBK/Shift-JIS/CP1251 in decode(), and expose an "encoding" option for text inputs; at minimum document the Latin-1 fallback and add a note/warning when the heuristic falls through. Add JVM tests for each legacy encoding.

### F15 — Low — reachableTargets includes the source format itself through cycles
**Evidence.** core/ConverterRegistry.kt:33-49 seeds the seen set empty, so any cycle back to the source re-adds it: jpg→pdf→jpg (ImageToPdf + PdfToImage) makes jpg a target of jpg; csv→tsv→csv (DataConverters) makes csv a target of csv; pdf→png→jpg→pdf (3 hops) makes pdf a target of pdf. RoutePlanner.plan returns emptyList() for from==to (core/RoutePlanner.kt:13), and today's picker filters source ids (ui/WorkbenchViewModel.kt:259), so the UI is safe by accident; any other caller (queue API, tests, future screens) can receive X→X and ConversionRunner would reject it with err_target_same (data/ConversionRunner.kt:42-46).
**Why it matters.** A public registry API that returns impossible targets is a latent trap for the next feature (batch presets, "convert to same" fix, engine tooling).
**Fix.** Add if (edge.target.id == from.id) continue in reachableTargets (or seed seen with from.id). Add a topology test asserting no source format appears in its own reachableTargets.

### F16 — Low — Animated GIF input silently becomes a still image
**Evidence.** image/ImageFormats.kt:21 lists gif as an input; decoding goes through BitmapFactory.decodeStream (image/ImageDecoding.kt:56-79), which returns the first frame; ImageToImageConverter returns ConversionResult(outputs) with no note (image/ImageToImageConverter.kt:61). There is no frame count check and no "first frame only" message. (Video→GIF keeps animation, video/VideoConverter.kt:63.)
**Why it matters.** A user converting an animated GIF to PNG/JPEG loses the animation with no warning; the catalogue says "GIF" as an image format next to WebP (which supports animation), so the expectation is animated. Once F1 lands, a one-line note makes this honest even without animation support.
**Fix.** Detect multi-frame GIF (ImageDecoder on API 28+, or Movie on 26-27) and attach a note "Only the first frame of the animated GIF was converted"; optionally offer APNG/GIF output later.

### F17 — Low — CSV→JSON drops cells beyond the header and pads short rows; TSV output uses CSV quoting
**Evidence.** data/JsonCsv.kt:24-46 builds each JSON object by iterating keys.indices only, so a row with more cells than the header loses the extra values silently, and a short row becomes "". An empty row is skipped only when it is exactly one empty cell (:36). CSV→TSV reuses Csv.escape (data/Csv.kt) for TSV output, so a field containing a tab is emitted as a double-quoted CSV field — most TSV consumers (and Excel on paste) do not interpret that quoting. Neither behaviour is documented or noted.
**Why it matters.** Silent data loss in a data-conversion path, and an interop surprise for the CSV/TSV pair, which is one of the most-used office-adjacent routes.
**Fix.** Either fail with a clear "row N has more cells than the header" error, or emit extra cells under generated keys / add an extra array field; use backslash escaping for TSV (or document that TSV is RFC-4180-style quoted). Add tests for ragged rows and embedded tabs.

### F18 — Low — WorkbookWriter creates a complete XLSX and only then throws "The file has no rows"
**Evidence.** office/WorkbookWriter.kt:63-74 closes the sheet and zip entries, flushes, and only then checks rowNumber == 0 and throws "The file has no rows to convert." The output file is already written at that point. ConversionRunner's finally deletes the work dir (data/ConversionRunner.kt:147), so the app is unaffected, but the engine contract ("throw means no output") is violated, and any direct/engine-level caller or future in-process retry keeps a valid empty workbook.
**Why it matters.** Low today, but these engine contracts are what the rest of the app relies on; a partial file plus an exception is the classic source of "success with empty output" bugs.
**Fix.** Count or peek the first row before writing the zip (or track rows in memory for the first 1 row), throw before opening the output stream; keep the current write-then-verify only for non-empty cases.

### F19 — Low — OCR masks every native failure as "pack unavailable", and the OCR image set differs from the image engine
**Evidence.** ocr/OcrEngine.kt catches Throwable at construction (:19), init (:27), page-seg (:37) and recognise (:47) and throws one constant "OCR pack unavailable on this device" (:56), so an OOM, a permissions bug, a corrupted traineddata, or a native ABI mismatch all present as "pack unavailable" (the user is told to download a pack that is already installed). ocr/OcrConverters.kt:22 accepts jpg, png, webp, bmp, gif, heic — no avif (documented at docs/models/integration.md:119) — while the image engine accepts avif (image/ImageFormats.kt:21); image→TXT via OCR therefore rejects an AVIF that image→JPG accepts.
**Why it matters.** Misdiagnosis wastes user support cycles ("I installed the pack and it still says install the pack"), and the inconsistent format sets make the same file convertible or not depending on target.
**Fix.** Split messages: missing/unreadable pack vs init failure vs recognition failure (keep the friendly text but add the cause in the exception message for history/logs); catch OOM separately with "This image is too large to process"; add avif to the OCR input set if BitmapLoader can decode it on API 31+ (it uses ImageDecoder) and gate by API as in F20.

### F20 — Low — HEIC/AVIF conversions are offered on OS versions that cannot decode them; the catalogue has no capability model
**Evidence.** core/FormatRegistry.kt:98-99 defines heic/avif with no minimum API; engine/image/ImageFormats.kt:20-21 notes HEIC needs API 28 and AVIF API 31 but still lists both unconditionally as inputs; decode guards throw a clear message at runtime (image/ImageDecoding.kt:82-94). The picker therefore offers HEIC→JPG and AVIF→PNG on API 26/27 (HEIC) and <31 (AVIF) and fails when the user taps Convert. FormatRegistry has no minApi/availability concept at all (core/FormatRegistry.kt:11-24, 152-158).
**Why it matters.** A conversion the app knows it cannot do is offered as if it can; the failure message is good, but the right UX is not to offer it (or to show it disabled with the reason). On a minSdk-26 app, API 26-27 devices are in scope.
**Fix.** Add minApi to FileFormat (or a capability map in the registry) and filter source/target lists in WorkbenchViewModel.computeTargets/reachableTargets by Build.VERSION.SDK_INT; keep the runtime messages as a backstop.

### F21 — Low — BuiltInConverters comment about registration order is false for equal-cost ties
**Evidence.** engine/BuiltInConverters.kt:21-22: "Order matters only for readability: the registry keys converters by source format and the route planner picks the cheapest path regardless of registration order." The planner's strict improvement check (core/RoutePlanner.kt:30) makes the first-registered converter win every equal-cost tie, which is exactly the documented pdf→txt shadowing (docs/models/integration.md:158-161). docs/qa/verification.md:118-120 and docs/models/integration.md itself contradict the comment; a future contributor reading the comment will not expect shadowing, and adding an edge with the same formats will silently change routing.
**Why it matters.** False local documentation next to the wiring point is how F2-class bugs get reintroduced; the integration point is explicitly Lead-owned, so it deserves a correct statement plus an explicit priority/ordering rule.
**Fix.** Replace the comment with the real rule ("equal-cost ties resolve to the earliest registered edge; keep that ordering deliberate"), or better, add an explicit priority/requiresTextLayer preference to Converter and have RoutePlanner break ties on it; then the pdf→txt fallback is a data change rather than an ordering accident. (The functional fix is F2.)

### F22 — Low — FormatRegistry MIME aliases point at formats that do not exist, and unknown MIME becomes a routeless ad-hoc format
**Evidence.** core/FormatRegistry.kt:40-48 maps application/vnd.ms-excel to byExtension["xls"] and application/msword to byExtension["doc"]; neither xls nor doc is in DATA, so both aliases return null. A file with a MIME not in the registry and an extension not in DATA becomes an ad-hoc FileFormat(id = extension, category = DATA) at :75-81, which the planner cannot route (no edges by construction) and which is displayed like a real catalogue format. build-verifier F6 covers the same legacy-alias issue from the build/docs side.
**Why it matters.** A .doc/.xls from the wild gets a generic unsupported error instead of an honest "legacy Word/Excel is not supported"; the dead alias code invites the belief that it works.
**Fix.** Delete the two dead aliases (or add doc/xls with truthful "recognised, not convertible" metadata, see F9) and make detect() mark ad-hoc formats explicitly ("unknown", not DATA) so the UI can say "unrecognised format" rather than showing a fake category.

### F23 — Low — TextIo's size-limit message hardcodes "24 MB" while callers pass 16 MB
**Evidence.** text/TextIo.kt:41-55 readAll throws "The file is too large for this conversion (limit 24 MB)." with the limit baked into the string, while ebook/EpubReader.kt:35,90 calls TextIo.readText(it, MAX_CHAPTER_BYTES) with 16 MB. A 17 MB legitimate EPUB chapter reports "limit 24 MB", which is both wrong and unactionable (the user cannot see the 16 MB chapter cap anywhere).
**Why it matters.** Minor, but it is the kind of wrong number that makes users distrust error messages; the cap also manages to reject a 17 MB chapter while claiming 24 MB.
**Fix.** Format maxBytes into the message (e.g. "limit 16 MB"), or have callers pass a human label; set the EPUB chapter cap and message from one constant.

### F24 — Low — VTT parser treats any cue text line starting with "NOTE"/"STYLE"/"REGION" as a comment block
**Evidence.** subtitle/SubtitleFormat.kt:86: if (line.startsWith("NOTE") || line.startsWith("STYLE") || line.startsWith("REGION")) { flush(); inNote = true; continue }. The WebVTT spec only reserves "NOTE" when followed by a space or the rest of the line, and STYLE/REGION only as block keywords at cue boundaries; here a normal subtitle line such as "NOTES from the meeting" or "STYLE is everything" is swallowed and the current cue is flushed early, losing text. A subtitle text line containing " --> " is likewise parsed as a timing line (:95-101) and truncates the cue.
**Why it matters.** Small but real silent subtitle corruption in the SRT/VTT route; this is a pure helper with 10 existing tests, so a fix plus tests is cheap.
**Fix.** Require NOTE followed by end-of-line/space, and treat STYLE/REGION only at block starts (blank line before them); require the timing regex to match the whole line (or to be at a cue start) before treating it as timing. Add tests for "NOTES ..." and a text line containing "-->".

### F25 — Low — Media progress formula assumes a unit; if getTime() is milliseconds (likely) every media job sits at 99% from the first callback
**Evidence.** media/FfmpegRunner.kt:286-305: progress = statistics.time * 1000.0 / totalMs, taken from Statistics (com.arthenica.ffmpegkit), while plannedDurationMs comes from MediaMetadataRetriever.METADATA_KEY_DURATION, which is milliseconds (:224-225). The formula therefore treats Statistics.getTime() as seconds. The dependency is dev.ffmpegkit-maintained:ffmpeg-kit-full:8.1.9 (app/build.gradle.kts:87), a drop-in fork of Arthenica's API (docs/research/android-stack.md:569). I could NOT verify the unit of getTime(): there is no sources jar in the Gradle cache I inspected, and web fetch was unavailable in this session (provider configuration error). Not run on a device. If getTime() returns milliseconds (the FFmpeg statistics scale, and the scale of every other duration in this file) or microseconds, the fraction is 1000x too large and the bar jumps to 99% on the first statistics callback — for the longest conversions, the only ones where progress matters. If it returns seconds, the formula is correct. The clamp and the monotonic percent (:299-304) keep it from crashing, and finish(success) forces 1f (:307-310), so the visible effect is a false "almost done", not a hang.
**Why it matters.** Cosmetic, but on a 20-minute video it makes the queue look stuck at 99%; if the unit is wrong the whole ProgressTracker is decorative.
**Fix.** Settle the unit with one device log (print statistics.time and wall-clock elapsed) or the fork's Statistics javadoc; then use the matching scale and document it. Extract getTime->fraction into a pure function and unit-test both the clamps and a known unit so a future dependency bump cannot silently change the scale.

### F26 — Low — OCR edges are registered unconditionally and the target picker never checks for the pack, so "to TXT" is offered where it cannot run
**Evidence.** engine/ocr/OcrConverters.kt:11-13 documents the deliberate choice ("The converters are always registered - the route stays visible so the picker can offer 'to TXT'"), and engine/BuiltInConverters.kt:34 registers them like any other family. The pack is only checked at conversion time: OcrSupport.languageCode reads ModelPacks.installedOcrLanguages and throws "Install the OCR pack (eng/ara) first" (engine/ocr/OcrSupport.kt:14,23-29; datapath check :31-37). ui/WorkbenchViewModel.kt:244-260 computes targets from reachableTargets alone and never consults ModelPacks, so a fresh install with no pack still shows TXT as a valid target for JPG/PNG/HEIC and PDF; tapping Convert then fails that item with the install message. The message is good and the route visibility is intentional, but the catalogue/picker claims a conversion the device cannot currently perform, and the same unconditional registration inflates the "reachable" claim in F8.
**Why it matters.** UX only (no data loss): the user picks a target, waits for a conversion, and only then is told to install something. Since OCR is the flagship feature, the first impression of it is a failed run unless the pack was installed beforehand.
**Fix.** Keep the registration (it is the right call for discoverability) but make the target availability-aware: when the source is an OCR source and the target is txt, grey the target out with the INSTALL_MESSAGE (or route to the model-pack install flow) when the selected language pack is absent. This also needs FormatRegistry/WorkbenchViewModel visibility of pack state, which F20's capability model would provide.

## Top-5 prioritized actions

1. **Fix scanned PDF→TXT in one Lead-owned file (F2).** In pdf/PdfToTextConverter.kt, on a blank extraction delegate to ocr/PdfTextConverter and return its result; keep the note fallback. This turns the flagship OCR feature on for the exact case it exists for. Then propagate notes (F1) so the page-window and no-text messages are visible.
2. **Strip media metadata (F6).** Add -map_metadata -1 -map_chapters -1 to every FfmpegArgs audio/video builder and assert it in FfmpegArgsTest.kt. One line, closes a real privacy hole in a privacy-first product, and is the cheapest possible way to make the privacy claim defensible.
3. **Harden the execution boundary (F5 + F7).** Timeout around completion.await() with session cancel + friendly failure; catch Throwable (rethrow CancellationException) at ConversionRunner and map OOM to a failed item; add the media input-size check. Without this, one long file can hang the queue and one OOM can kill the app — both worse than any conversion-quality defect.
4. **Make outputs match requests (F3 + F4).** Fan out multi-output intermediate steps (or forbid them in the planner), and honour options.pages in PdfToTextConverter. These are the two remaining silent-data-loss/wrong-output paths.
5. **Correct the claims and lock them with tests (F8, F9, F12, F13).** State 32 converters / 172 edges / 171 pairs / 11 families / 10 productive; state 48 recognised, 39 convertible (or add the missing edges); stop claiming resize until a resize control exists; add the pure-JVM topology test that would have caught the duplicate pdf→txt edge, the dead formats and the mislabel. Keep every future edge change behind that test.

## What is done right (only what this seat actually checked)

- **No shell surface in FFmpeg.** Commands are Array<String> arguments, never a shell string; -y is explicit; trim uses -ss/-to as input options so duration is end-start (engine/media/FfmpegArgs.kt:166-169, verified by FfmpegArgsTest:82-99). No GPL encoders are referenced (test FfmpegArgsTest:257-266).
- **FFmpeg result verification is real.** Return code is checked (ReturnCode.isSuccess), cancelled is distinguished, and the output file must exist and be non-empty (engine/media/FfmpegRunner.kt:111-143). Software fallback is limited to mp4/mkv (VideoConverter.kt:52-61) and the failed output is deleted before retry (:54).
- **Temp hygiene is good.** Media input is deleted in finally, output removed when the block did not complete (FfmpegRunner.kt:63-77), stale cache pruned at 6 hours (:242-247), cancellation checked inside copy loops (:205) and archive loops. PDF/office/EPUB/OCR temp files are deleted in finally blocks; PDFSupport has a 500 MB cap and free-space check (engine/pdf/PdfSupport.kt:18,29-34).
- **Archive safety is structurally strong for a converter.** Nothing is extracted to disk, so zip-slip cannot be exploited by conversion; entry names are normalised and traversal/absolute/drive/NUL/long-segment names rejected (engine/archive/ArchiveGuards.kt:25-44); entry and expanded-size caps exist; 7z has a 64 MB memory limit and anti-items are skipped (ArchiveConverters.kt:306-353); tar symlinks/hardlinks are skipped and duplicates deduped with a planned note (:240-285).
- **OOXML/EPUB XML handling.** DOCTYPE processing is disabled (XXE mitigation) on a pull parser (engine/office/OoxmlPackage.kt:194-208), package entries are counted lazily with 2 GB expansion and 512 MB per-part caps (:88-135), and the same SafePackage is reused for EPUB.
- **PDF password and memory handling.** PDFBox uses MemoryUsageSetting.setupTempFileOnly() and maps InvalidPasswordException to a clear message (pdf/PdfToTextConverter.kt:75-89); PdfRenderer maps SecurityException to the same class of message (pdf/PdfToImageConverter.kt:70-79); page spans, clamping and de-duplication are robust (pdf/PdfPageSelection.kt, 8 tests); partial page outputs are deleted on failure (:112-115); cancellation is checked per page.
- **Image resource discipline.** OOM is mapped to a friendly ConversionException in image/ImageToImageConverter.kt:29-43, image/ImageToPdfConverter.kt:38-39, pdf and OCR paths; JPEG alpha is flattened to white (image/ImageToImageConverter.kt:79,106-114); outputs are deleted on failure (needle: :62-64); bitmaps are recycled in finally blocks; HEIC/AVIF guards produce OS-specific messages rather than decode crashes.
- **OCR lifecycle.** One TessBaseAPI per conversion, initialised once, recycled via use/close (ocr/OcrEngine.kt:15-53, ocr/ImageToTextConverter.kt); output text is normalised (ocr/OcrText.kt:7-16); empty recognition throws a hint instead of reporting an empty file (ocr/OcrFiles.kt:10-26); one engine instance serves all pages of a PDF.
- **Router design.** Uniform-cost Dijkstra is the right model for this graph (all edges cost one file operation): correct for maxHops, correct unreachable handling, no cycle risk because cost strictly increases, from==to short-circuits, and the runner/picker share MAX_HOPS=3 (data/ConversionRunner.kt:180, ui/WorkbenchViewModel.kt:244-260). Registration order has no effect on path length, only on equal-cost tie choice.
- **Graph wiring discipline.** Every family is wired exactly once in engine/BuiltInConverters.kt:24-36; converters are format-agnostic or switch explicitly on the source format, and no cross-product pair exists that would throw for a wrong pair; upscale returns emptyList deliberately and the reason is documented (engine/upscale/UpscaleConverters.kt:6-21); the multi-output PDF→PNG path correctly publishes every page (data/ConversionRunner.kt:113-120) and gives extra outputs unique names (data/ConversionRunner.kt:186-198).
- **Verified counts.** 48 catalogue formats (core/FormatRegistry.kt:90-148); 32 converter implementations/ids; 15 JVM test classes and 131 @Test; 51 engine files; 172 directed registry edges / 171 distinct pairs.
