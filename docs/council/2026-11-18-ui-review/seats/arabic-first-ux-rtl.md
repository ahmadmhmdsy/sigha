## 2. New findings / regressions (no P0, no new P1)

**2.1 [P2] The plural category for "pages limited" is chosen from the wrong number.** `ui/NoteUi.kt:19-24` passes `note.total` as the quantity; the note is `PagesLimited(read = max, total = pageCount)` (`model/OcrPageRange.kt:30-39`), and the items are `values-ar/strings_ui.xml:33-40` / `values/strings_ui.xml:37-40`. The sentence is about the pages read (the 50-page cap), but Arabic now picks the category of the page count: a 101-page scan renders the `one` item — **"قُرئت الصفحة الأولى من أصل صفحة واحدة."** ("the first page was read of one page") — although 50 were read; 102 gives the dual, and 103-110 the `few` item ("قُرئت أول 50 صفحات من أصل 103"). English is unaffected (every reachable total is `other`: "Only the first 50 of 101 pages were read."), which is exactly why this would ship unnoticed — the defect exists only in the translated locale. Introduced by the fix pass; no screenshot contains a note (§4).

**2.2 [P2] The Arabic `two` item for the same plural loses the dual.** `values-ar/strings_ui.xml:36` "قُرئت أول صفحة من أصل صفحتين." should be "أول صفحتين" (compare the correct `:44`). Reachable only through 2.1's wrong quantity (a correct quantity walks into `many`), so the only sentence users can ever see in that row is grammatically wrong.

**2.3 [P2] Bidi is untouched, and the rewritten surfaces reproduce the pattern.** The pass renders Arabic at five interpolated sites — pack title in the download dialog (`WorkbenchScreen.kt:761-768`, `ModelPacksScreen.kt:121-127`), metered/resume notes (`WorkbenchScreen.kt:769-781`), install-size label (`:743`), summary separator (`values-ar/strings.xml:90`) — with no isolation API, exactly the raw interpolation baseline #8 asked to replace; the one-line ellipsized saved path (`ui/QueueScreen.kt:280-288`) is unchanged, so every successful save still renders its Arabic sentence around an LTR path and can hide the file name.

**2.4 [P2] Three locale sources now disagree.** Arabic typography uses configuration locales (`Theme.kt:92-97`); the privacy asset and all dates/sizes use `Locale.getDefault()` (`PrivacyScreen.kt:60-61`, `Formatters.kt:19-29`); the OCR first-run default is computed once from configuration (`SettingsStore.kt:64-68`). The moment per-app Arabic exists (#10), an English-locale phone would show Arabic chrome with an English policy and English dates. Evidence cannot disprove it: on this AVD the default locale also resolved Arabic (visible Arabic date/AM marker in `history-ar.png`).

**2.5 [P3] Pack identity still starts with Latin.** `pack_ocr_title` = "OCR: الإنجليزية + العربية" (`values-ar/strings.xml:215`), so Compose's first-strong rule sets the card title's paragraph LTR and the dialog still splices the title into a sentence (`WorkbenchScreen.kt:764`), contrary to the baseline's "own line" fix. `model-packs-ar.png`/dialog screenshot render acceptably because of the «» quotes, but the reading order starts on the wrong glyph for the Arabic-defining feature.

**2.6 [P3] The new Arabic invariants are not covered by tests.** 137 tests / 16 classes (`docs/qa/evidence/verify-20261117-231022.json` `facts.unitTests`), none for EN↔AR resource parity, plural categories, note localization or Arabic digit normalization: `normalisePageSelection` is private and untested, `OcrLanguages.defaultForLanguage` untested, `OcrPageRangeTest` covers logic only. 2.1 is exactly what a plural test would catch; the 254-key/96-form Arabic set can drift silently (parity in this report was checked by script, not by CI).

**2.7 [P3] The privacy screen shows the same date two ways.** Top card "17 تشرين الثاني (نوفمبر) 2026" (`values-ar/strings_legal.xml:25`) above a policy whose first line is "تاريخ السريان: 17 نوفمبر 2026" (`assets/legal/privacy-policy.ar.md:3`), both visible in `privacy-policy-ar.png`; `values-ar/strings_legal.xml:22` also still claims the English asset is rendered.

**2.8 [P3] The details-label contract is still dishonest.** `ui_details_show/hide` = "إظهار/إخفاء التفاصيل التقنية" (`values-ar/strings_ui.xml:12-13`) wraps English engine diagnostics; `engine/pdf/PdfToTextConverter.kt:105-121` and `engine/ocr/OcrSupport.kt:14-17` still throw English with no typed kind (`FailureUi.kt:12-27`). The headline is Arabic, so this is opt-in, but it is the last place the language changes under the user.

Fixing it needs no device evidence and closes the largest remaining gap.
